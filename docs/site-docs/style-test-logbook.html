Foundation · Ownership

System topology

Four ownership layers keep the ship slice readable: the executable drives the game, the game owns RPG behavior, a deliberately small framework holds proven structure, and the platform wraps Windows.

  • Primary sourcesrc/
  • Decision ownerJamie
  • StatusImplemented

Why four layers exist

The split makes ownership visible. It is intentionally narrower than a general engine: abstractions enter Framework only after the ship slice demonstrates real reuse. Everything that knows about missions, keys, lanterns, or battles stays in Game.

LayerOwnsDoes not own
ApplicationWin32 startup, configuration, frame timing, native event translation.RPG rules or scene content.
GameScenes, objects, scripting, RPG state, battles, menus, effects.Raw Direct2D, XAudio2, or Win32 calls.
FrameworkThe small proven scene, layer, object, camera, and sprite structure.Missions, inventory, battles, or other RPG policy.
PlatformGraphics, text, audio, input, logging, loaded asset definitions.Gameplay intent or content decisions.
Boundary test

If a type mentions a mission, item, battle reward, NPC duty, or semantic ground behavior, it belongs to Game unless Jamie explicitly decides otherwise.

A concrete interaction

  1. YAML places the door.The scene map defines its sprite, position, and local interaction trigger.
  2. C++ notices the player.The interaction point picks the nearest eligible object on the primary-action edge.
  3. Lua decides what it means.A rule table selects the script; it calls narrow functions like Say or SetTag.
  4. C++ applies it safely.Requests are validated, queued, and drained after traversal.
